# 校務系統開發規畫

## 一、專案目標

建立一個可擴充的校務系統，提供不同校務角色登入後使用相應功能。系統先以輕量 SQLite 資料庫保存帳號、課程、選課與請假資料，並透過假資料完成後續測試。

## 二、使用者角色與權限

| 角色 | 權限 |
| --- | --- |
| 管理員 | 管理使用者與系統設定，查看課程、課表及所有請假紀錄，審核請假。 |
| 行政 | 維護課程資料，查看課程與請假紀錄，審核請假。 |
| 學生 | 登入、查詢課程、選課、查看個人課表、提出及查詢請假申請。 |
| 老師 | 查看授課課程與課表，查看並審核學生請假申請。 |

## 三、核心功能

1. 使用者登入與身分驗證。
2. 依角色限制 API 與資料操作權限。
3. 課程查詢，可依課程代碼或名稱搜尋。
4. 學生選課與選課人數上限檢查。
5. 顯示學生已選課程或老師授課課程的課表。
6. 學生提出請假申請。
7. 行政、老師與管理員審核請假申請。
8. SQLite 自動建立資料表並載入假資料。

## 四、系統架構

目前採用簡單的分層方向：

```text
Client / 前端
      ↓ HTTP JSON API
API Handler（登入、課程、選課、課表、請假）
      ↓ 角色權限檢查
資料存取層
      ↓
SQLite（school.db）
```

前端使用 HTML、CSS 與 JavaScript，透過相同來源的 API 與後端溝通。後端已將 `app.py` 拆分為 `auth`、`courses`、`enrollment`、`leave`、`admin`、`database` 與 `server` 模組。新增功能可透過 `extensions.register()` 註冊路由，沿用登入、權限及資料庫機制。

## 五、資料庫規畫

| 資料表 | 主要用途 |
| --- | --- |
| `users` | 保存帳號、密碼雜湊、角色與姓名。 |
| `courses` | 保存課程代碼、名稱、教師、學分、容量、上課時間與教室。 |
| `enrollments` | 記錄學生與課程的選課關聯，避免重複選課。 |
| `leave_requests` | 記錄學生請假日期、原因、審核狀態與審核人員。 |

密碼使用帶有隨機 salt 的 Argon2id 雜湊保存。另加入 `sessions`、`settings`、`audit_logs` 與 `metadata` 資料表，保存可撤銷且有期限的登入狀態、系統設定、操作紀錄與初始化狀態。SQLite 啟用外鍵、WAL、索引與交易；提供線上備份及日期格式驗證。

## 六、API 規畫

| 方法 | 路徑 | 目的 | 權限 |
| --- | --- | --- | --- |
| `POST` | `/api/login` | 登入並取得 token | 公開 |
| `GET` | `/api/courses` | 查詢課程 | 已登入 |
| `POST` | `/api/enroll` | 新增選課 | 學生 |
| `GET` | `/api/schedule` | 學生查個人課表、老師查授課課表、行政與管理員查全校課表 | 已登入 |
| `POST` | `/api/leave` | 提出請假 | 學生 |
| `GET` | `/api/leave` | 查詢請假紀錄 | 學生、行政、老師、管理員 |
| `POST` | `/api/leave/{id}/review` | 審核請假 | 行政、老師、管理員 |

## 八、測試規畫

測試分為單元測試、系統測試與 E2E 測試，從個別邏輯、完整 API 系統到使用者實際流程逐層驗證。

### 8.1 單元測試（Unit Test）

針對單一函式或單一模組進行測試，使用測試資料庫或 mock 隔離外部依賴，確保程式邏輯正確。

- 測試密碼雜湊結果與登入帳密比對。
- 測試 token 建立、解析與無效 token 判斷。
- 測試角色權限檢查：允許角色通過，不允許角色回傳權限錯誤。
- 測試課程搜尋可依課程代碼或名稱篩選。
- 測試選課重複檢查與課程人數上限檢查。
- 測試請假資料的日期、原因與狀態驗證。
- 測試資料庫初始化會建立必要資料表與假資料。

### 8.2 系統測試（System Test）

啟動完整 API 伺服器與 SQLite 資料庫，透過 HTTP 請求驗證各功能模組整合後的行為。

- 驗證四種角色皆可使用正確帳密登入，錯誤帳密回傳 `401`。
- 驗證未登入呼叫受保護 API 回傳 `403`。
- 驗證學生查詢課程、選課後可在課表中看到該課程。
- 驗證學生不能重複選課，課程額滿時不能再選課。
- 驗證學生提出請假後，行政、老師與管理員能查到申請。
- 驗證具權限人員審核後，請假狀態正確更新。
- 驗證學生只能查詢自己的課表與請假紀錄。
- 驗證服務重新啟動後，SQLite 中的使用者、選課與請假資料仍存在。

### 8.3 E2E 測試（End-to-End Test）

模擬真實使用者從登入到完成業務流程的完整操作，確認前端（未來加入）、API 與資料庫能共同運作。

#### 學生流程

1. 使用 `student1` 登入。
2. 查詢「程式設計」課程。
3. 選取課程並確認選課成功。
4. 開啟課表並確認課程、星期、節次與教室正確顯示。
5. 提交請假申請。
6. 查詢請假紀錄並確認狀態為 `pending`。

#### 行政或老師流程

1. 使用 `office` 或 `teacher1` 登入。
2. 查詢所有請假申請。
3. 審核學生請假申請。
4. 確認學生再次查詢時，狀態已變更為 `approved` 或 `rejected`。

#### 權限與錯誤流程

1. 使用學生 token 嘗試審核請假，確認系統拒絕操作。
2. 使用不存在的課程編號選課，確認回傳錯誤。
3. 使用過期或偽造 token，確認無法存取受保護資源。
